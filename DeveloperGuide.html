Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores each person's care notes as a Remark, which may have no notes.
  • stores each person's priority tags as a Set<Tag>. Valid names are HIGH, MEDIUM, and LOW; the set must be empty or contain one priority.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • stores each contact as a JsonAdaptedPerson with at most one JsonAdaptedTag, because a contact can have at most one priority.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Saving data

CareBook saves the contact list to data/contacts.json only after a command that changes it. Each Command has a modifiesData() method that returns true by default. Commands that only change what is displayed or show information (list, find, filter, sort, view, clear, help and exit) override it to return false. delete INDEX without /confirm only shows a warning, so it returns false too. Every other command, including archive, checkup, edit and remark, saves.

The sequence diagram below shows how LogicManager decides whether to save after executing a command.

  1. LogicManager parses the command text into a Command, keeps a copy of the address book, and executes the command.
  2. It then calls modifiesData() on the command.
  3. If the command changes data, LogicManager gets the address book from the Model and passes it to Storage#saveAddressBook. If the save fails, LogicManager restores the copy with Model#setAddressBook and throws a CommandException. The user sees Could not save data to file ... (or a message about insufficient permissions), followed by The command was undone, so your contacts are unchanged., and CareBook keeps running.
  4. Otherwise, LogicManager only logs that the save was skipped, and the data file is left as it is.

Design consideration: if a failed save left the change in memory, the app would show a change that is not in the file. It would be lost on exit, or saved later by an unrelated command, and retrying a failed add would be rejected as a duplicate. Undoing the command keeps the app and the file the same. Restoring the address book also clears the details panel, which is acceptable after an error.

Design consideration: saving after every command would be simpler, but it would rewrite the data file even when nothing changed. Skipping the save for commands that only show information means a command such as list never overwrites a data file that the user is editing by hand.

Add command

The add command creates an active contact with a name, patient phone number, family phone number and address. Patient email, family email and a priority tag are optional. The command word is case-insensitive: add, Add and ADD follow the same parsing and execution path.

Parsing and validation

AddressBookParser#parseCommand() recognises the command word and delegates to AddCommandParser#parse(). The parser tokenizes the supported prefixes, checks required fields and rejects repeated non-tag prefixes before constructing the field objects and a Person. Supported prefixes are /name, /patientNo, /familyNo, /pEmail, /fEmail, /address and /tag. Only the /tag prefix is case-insensitive. The legacy /email prefix is rejected with instructions to use /pEmail or /fEmail.

Every / must start a complete recognised prefix, separated from its value by whitespace. A literal / cannot be stored in any field value. Strict tokenization therefore rejects /address 4 St /phone 123, /addressExtra 4 St and /address 4/5 Main St instead of silently storing the extra text as an address. The invalid-format response includes AddCommand.MESSAGE_USAGE, which also supplies the Add entry in the Help window and explains the slash restriction.

ParserUtil validates individual fields and trims surrounding whitespace. Name also collapses repeated spaces, so Kim Lee is stored as Kim Lee and cannot bypass duplicate detection through spacing. Priority normalization and validation follow the rules in Priority tags.

Duplicate detection and execution

AddCommand#execute() checks the candidate against the full address book, including archived contacts; the current display filter and sort order do not limit duplicate checks. Person#isSamePerson() and UniquePersonList enforce the contact identity rules:

  • A matching patient phone number or a matching non-empty patient email is a duplicate, even if the names differ. Patient email comparison ignores case; two omitted patient emails are not a match.
  • A shared name alone is allowed when the patient contact details and address distinguish the contacts.
  • The same name and address require a name differentiator. Names are compared ignoring case after normalization; addresses are compared ignoring case and all whitespace. This comparison does not remove internal spaces from the stored address. Different names may share an address.

The sequence diagram below shows a successful add after input and duplicate validation. Error branches stop before the model is changed; their messages are described below.

  1. AddCommandParser creates the validated Person and an AddCommand containing it.
  2. AddCommand calls Model#hasPerson() to check for a duplicate. A duplicate patient phone or email produces AddCommand.MESSAGE_DUPLICATE_PERSON: This person already exists in CareBook.
  3. A same-name, same-address conflict without a duplicate patient phone or email instead produces WARNING: Same Address. Include a differentiator such as a number (eg Alice 2) or surname.
  4. Otherwise, Model#addPerson() adds the contact and restores the active list. The command returns the new contact's details in a CommandResult.
  5. AddCommand#modifiesData() returns true, so LogicManager saves the updated address book through Storage#saveAddressBook().

Error handling: Invalid prefixes, missing required fields, duplicate prefixes and invalid values cause a ParseException. Duplicate contacts cause a CommandException. Neither path adds a contact or saves a partial entry. Shared family phone numbers and family emails are allowed; patient contact details provide the uniqueness checks.

Design consideration: Normalizing names when constructing Name gives parsing, storage loading and duplicate checks the same representation. Checking the full address book prevents a hidden or archived contact from being added again, while allowing different patients to share a name or family contact.

Viewing a contact's full details

The view INDEX command displays one contact from the currently displayed list and returns their full details in a dedicated scrollable panel. It preserves the current display filter without modifying stored contacts.

The sequence diagram below shows a successful view 1 command, assuming at least one contact is displayed. It focuses on command parsing and execution; helper calls and UI updates are omitted for clarity.

  1. LogicManager#execute() passes the input to AddressBookParser#parseCommand(), which recognises view and creates a ViewCommandParser.
  2. ViewCommandParser#parse() uses ParserUtil#parseIndex() to validate the argument and creates a ViewCommand containing an Index. The user-facing index is one-based; Index#getZeroBased() converts it to the corresponding Java list index during execution.
  3. ViewCommand#execute() obtains Model#getFilteredPersonList() and checks that the index is in range. The index refers to the displayed list, so after find Alice, view 1 selects the first search result.
  4. The command retrieves personToView, then calls Model#selectPerson(personToView) without changing the filter. The UI observes the read-only selectedPersonProperty() through Logic to refresh PersonDetailsPanel and highlight the selected contact in PersonListPanel.
  5. A new CommandResult confirms the selected contact's name; full details appear in the dedicated panel. LogicManager checks ViewCommand#modifiesData(), which returns false, and skips saving. MainWindow displays the returned feedback in ResultDisplay.

Every successful view result also sets CommandResult#isViewRequested() to true. MainWindow uses this request to refresh highlighting and scroll the selected contact into view. Unlike a selection change listener, this also runs when the user repeats view for the same contact after scrolling away. No temporary deselection or stored-data change is needed to trigger the UI action.

Error handling: Missing, non-numeric or non-positive indexes cause the parser to throw a ParseException with the command usage. During execution, ViewCommand#validateTargetIndex() distinguishes an empty displayed list from an index outside a non-empty list. An empty display produces recovery instructions to use list or find KEYWORD; an out-of-range index reports the supplied index, displayed count and valid range. Both cases throw a CommandException and never select from the full stored list as a fallback. These errors leave stored contacts, selection and the display filter unchanged.

Selection lifecycle: ModelManager stores a transient contact reference, not its displayed index. After a command and its required save succeed, LogicManager clears selection unless Command#preservesPersonSelection() returns true; ViewCommand overrides that method to preserve it. This closes the details panel after other successful commands without resetting their filter or sort. Parse errors and command-validation failures never reach this cleanup, so they preserve selection. The following model-level rules also protect callers that update contacts directly: setPerson replaces that reference when the selected contact is edited, including a name change. Deleting that contact or replacing the address book clears selection. Editing or deleting a different contact leaves selection unchanged. Updating a filter clears selection only if it hides the contact; therefore clear also hides the details panel. With no selection, the panel and its placeholder are invisible and unmanaged, so they reserve no layout space. Selection is never serialized.

setPerson clears selection instead of retaining the replacement if it leaves the displayed list. This also handles archiving an active selected contact and restoring one from the archive list.

Cross-feature integration: getFilteredPersonList() exposes the SortedList over the filtered contacts, so view, remark and checkup use the same displayed indices. Sorting keeps the selected contact at model level rather than selecting whichever contact moves into its former row; the command processing policy then clears selection after a successful sort. PersonDetailsFormatter includes the optional checkup appointment and every numbered remark. Replacing the selected immutable Person through setPerson() refreshes these details without changing the current filter or sort.

Design rationale: a separate details panel lets caregivers read complete contact information while retaining their position in a search or filtered list. Content-sized panels grow up to height caps, with vertical scrolling and bounded bottom-edge resize handles for longer content. The feedback panel uses the same sizing behaviour for every command. A coloured card border and a Selected contact heading link the details to the list without treating a changing list index as a permanent contact identifier.

Clearing the display and exiting

AddressBookParser#parseCommand() recognises the lowercase clear and exit command words and rejects non-blank arguments before creating their command objects. Other letter-case variants are unknown commands. A parse error leaves the display and stored contacts unchanged.

ClearCommand#execute() calls Model#updateFilteredPersonList(PREDICATE_SHOW_NO_PERSONS). The predicate hides every contact in the current display but does not remove any from the address book. When the selected contact is no longer in the filtered list, ModelManager sets its transient selection to null; the details panel and highlight disappear. list restores the active list, list archive restores the archive list, and find searches within the current scope. ClearCommand#modifiesData() returns false, so LogicManager does not save the display change.

ExitCommand#execute() returns a CommandResult with the exit flag. MainWindow checks that flag after showing the feedback and calls its exit handler. ExitCommand#modifiesData() also returns false; neither an invalid exit command nor a successful one changes contact data.

Editing a contact

edit INDEX [/name NAME] [/patientNo PATIENT_PHONE] ... [/tag PRIORITY] changes the given fields of a displayed contact and keeps everything else, including the contact's notes, checkup appointment, checkup mark and archived status.

  1. EditCommandParser splits the input with ArgumentTokenizer#tokenizeStrict(), which rejects unknown prefixes and / inside a value. The preamble is the index.
  2. Each given field is parsed with ParserUtil and stored in an EditPersonDescriptor. A field that is not given stays empty in the descriptor, which means "keep the current value".
  3. EditCommand#execute() checks the index against the displayed list, then builds the edited contact in createEditedPerson() from the descriptor and the current contact.
  4. The edited contact is rejected if another contact has the same patient phone number or patient email (Person#hasSamePatientContactDetails()), or the same name and address (Person#hasSameNameAndAddress()). Archived contacts count too.
  5. Model#setPersonKeepingDisplayed() replaces the contact. The displayed list (search results, archive list and sort order) stays as it is, and the edited contact stays in it even if it no longer matches the search, so the indices on screen do not change. ModelManager keeps a set of such contacts, and the filtered list shows a contact if it is in the set or matches the search. A later Model#setPerson() on a kept contact (e.g. by checkup or mark) keeps the new contact in the set, unless the change moves it out of the current list, as archive does. The next list, find or filter empties the set. LogicManager then saves the data.

Keeping, setting and removing an email: emails are optional, so edit has to tell three cases apart. A missing /pEmail keeps the email, /pEmail new@example.com sets it, and an empty /pEmail removes it. An empty Optional<Email> alone cannot separate "keep" from "remove", so EditPersonDescriptor also records isPatientEmailEdited (and isFamilyEmailEdited). EditCommand#chooseEmail() uses the new email only when the flag is set. Tags work the same way: a single empty /tag clears the priority.

Design considerations

Aspect: how to remove an optional field

  • Alternative 1 (current choice): an empty value, e.g. edit 1 /pEmail.
    • Pros: One command, using the prefix the user already knows.
    • Cons: Needs the extra "edited" flag in EditPersonDescriptor.
  • Alternative 2: a separate command or keyword, e.g. unset 1 /pEmail or /pEmail none.
    • Pros: Removing data is more explicit.
    • Cons: Another command or keyword to learn, and none could not be used as a real value.

Aspect: what the list shows after an edit

  • Alternative 1 (current choice): the same list, with the edited contact kept in it.
    • Pros: The indices the user just saw stay valid, so a follow-up command changes the intended contact.
    • Cons: The list can contain a contact that no longer matches the search until the next list or find.
  • Alternative 2: the full active list (CareBook's behaviour before v1.5).
    • Pros: Always shows every contact.
    • Cons: The user loses their search, and indices change under them.

Priority tags

Priority tags use the existing /tag prefix and Tag model, with names restricted to HIGH, MEDIUM, and LOW.

Model and validation

Tag is immutable and stores its priority as a String in tagName. Tag.isValidTagName uses Priority.valueOf to check whether the input names a Priority enum constant. The enum is the source of accepted values (HIGH, MEDIUM, and LOW); there is no separate validation regex. Matching is exact and case-sensitive. Unknown names return false by catching IllegalArgumentException, while null input throws NullPointerException. The constructor does not trim or change case and rejects invalid names with IllegalArgumentException.

Person copies tags into a HashSet and exposes an unmodifiable set through getTags(). Equality and hashing of Tag use tagName, so duplicates collapse into one tag. The Person constructor rejects sets with more than one tag using Person.MESSAGE_TAG_COUNT_CONSTRAINTS: A contact can have at most one priority tag. This keeps the model valid even when constructed outside the command parsers.

Command parsing and editing

AddCommandParser and EditCommandParser collect all /tag values. ArgumentTokenizer recognizes /tag ignoring case and maps variants such as /TAG and /TaG to the canonical PREFIX_TAG. It preserves argument values and the matching rules for other prefixes. ParserUtil.parseTag trims each value and converts it to uppercase using Locale.ROOT before enum validation. This accepts mixed-case command input independently of the system locale while keeping model and stored values uppercase. Invalid values cause a ParseException with Tag.MESSAGE_CONSTRAINTS: Tag names must be HIGH, MEDIUM or LOW. ParserUtil.parseTags removes duplicates after case normalization and rejects more than one distinct priority with a ParseException using Person.MESSAGE_TAG_COUNT_CONSTRAINTS. It returns an empty set or a singleton set; invalid input prevents the command from changing the model.

  • For add, omitting /tag produces an empty set. An empty /tag value is invalid.
  • For edit, omitting /tag leaves tags unchanged. Providing values replaces the whole set through EditPersonDescriptor and EditCommand.
  • EditCommandParser.parseTagsForEdit treats a single empty /tag as an empty set, clearing all tags. An empty value combined with other /tag occurrences is invalid.

For example, edit 1 /tag MEDIUM replaces all existing tags with MEDIUM, edit 1 /tag HIGH /tag LOW is rejected, and edit 1 /tag clears them.

Checkup appointments

The checkup INDEX dd/mm/yyyy HH:mm command sets or replaces an appointment for a displayed contact. checkup INDEX delete removes it. The command word and delete keyword are case-insensitive.

Parsing and validation

AddressBookParser delegates to CheckupCommandParser, which trims surrounding whitespace, collapses repeated whitespace and parses the displayed Index. A delete request creates a deletion command; otherwise the command retains the date/time input until the target contact can be checked during execution. Missing arguments and invalid index syntax cause a ParseException with the command usage.

CheckupCommand#execute() validates the displayed index before retrieving the contact. For scheduling, the archived-contact check runs before date/time validation, so an archived contact produces Appointments cannot be made with archived contacts. Unarchive the contact to do so. even if the supplied date or time is invalid. This ordering requires date/time validation to be deferred until execution.

CheckupAppointment uses the fixed dd/MM/uuuu HH:mm formatter with Locale.ROOT and ResolverStyle.STRICT. Impossible dates and times are rejected without rounding. The appointment is a LocalDateTime; comparison with the current local date and time rejects earlier times today as well as past dates. The error is Checkup date and time must not be in the past. Regional date-display and 12/24-hour settings do not affect parsing or comparison, but the system clock and timezone determine now.

Before changing the model, the command checks all active contacts for an equal CheckupAppointment, excluding the target contact. A shared slot is allowed only when every contact already booked at that slot has the same familyNo as the target. Hidden active contacts participate; archived contacts are excluded. A conflict throws a CommandException with A contact with this booking date and time already exists. Only contacts with the same family HP can be booked at the same time. No appointment, mark, selection or stored contact is changed by a rejected booking.

The sequence diagram below shows scheduling or deleting a checkup using the displayed contact index. Validation failures stop before the model is changed or saved. Field-construction helpers and individual UI observer calls are omitted for clarity.

Model, UI and storage

The command creates an immutable replacement Person and calls Model#setPerson(), preserving the other contact fields. Replacing an appointment clears checkupMarked; assigning the same appointment preserves its mark. A deletion clears both the optional appointment and its mark, and fails with This contact has no checkup appointment to delete. if no appointment exists.

PersonCard shows the appointment row and a [ ] or [X] indicator only while an appointment is present. After deletion, the row is invisible and unmanaged, so it reserves no layout space, and the indicator is omitted. Updating a selected immutable contact refreshes the details panel. The command uses the displayed list index and preserves sorting and filtering; if a view predicate excludes the replacement because its fields changed, the display is refreshed to keep the updated contact visible.

CheckupCommand modifies data, so LogicManager saves successful changes through Storage. JsonAdaptedPerson stores checkupAppointment and checkupMarked; absent appointments are represented by null and cannot be marked. Stored past appointments remain loadable because the constructor validates the date/time format, while the command enforces the not-in-the-past rule for new bookings.

Design consideration: Checking archive status and booking conflicts during execution uses the current model state and ensures the displayed index refers to the selected contact. Keeping parsing and storage formatting independent of regional settings makes saved appointments portable between computers.

Removing a checkup appointment

checkup INDEX /delete removes the selected contact's appointment and checkup mark. CheckupCommandParser normalizes whitespace, validates the displayed index and recognizes /delete ignoring letter case before creating the command through CheckupCommand.delete(index). The slash is required; bare delete is not recognized as the deletion option and follows the existing date-validation path during execution.

CheckupCommand represents deletion with a null appointmentValue. During execution, it validates the displayed index and checks that the contact has an appointment, otherwise throwing MESSAGE_NO_APPOINTMENT. It replaces the immutable Person with an absent appointment and a cleared checkup mark through Model#setPerson(), preserving the remaining details. The contact card hides the appointment row and removes the mark indicator. Deletion also works for archived contacts; the archive, date/time and booking conflict checks apply when setting an appointment. LogicManager saves the changed contact as usual.

Remarks

The remark command keeps numbered care notes on a contact, such as allergies or visiting rules. One command word accepts four formats:

  • remark INDEX NOTE adds a note after the contact's last note.
  • remark INDEX /edit NOTE_NUMBER NOTE replaces the note with that number.
  • remark INDEX /delete NOTE_NUMBER deletes the note with that number.
  • remark INDEX /clear deletes all of the contact's notes.

Model and storage

Remark is an immutable list of notes held by every Person. A person with no notes holds an empty Remark (equal to Remark.EMPTY), so Person#getRemark() never returns null. Each note must not be blank or start with a space, a person cannot have the same note twice, and the notes can have at most Remark.MAX_TOTAL_LENGTH (500) characters in total, which stops one contact's card from filling the list. The Remark constructor enforces both rules, so an invalid remark cannot exist in the model.

The notes count towards Person#equals() but not Person#isSamePerson(), so notes never decide whether two contacts are the same person. EditCommand copies the remark unchanged into the edited person. JsonAdaptedPerson stores the notes as a remarks list of strings. A missing remarks field loads as no notes, so data files saved by v1.4 and earlier still load.

Parsing and execution

The sequence diagram below shows a successful remark 1 Diabetic command.

  1. RemarkCommandParser#parse() takes the first word as the index. It then looks at the next word: /edit, /delete and /clear, in any letter case, select those actions. Anything else means the whole rest of the input is a new note.
  2. The parser does not use ArgumentTokenizer, so a note is kept exactly as typed even when it contains text such as /tag. Prefixes would split such a note into fields.
  3. The parser creates the command through a factory method: RemarkCommand#add(), #edit(), #delete() or #clear(). Each stores the action and only the values that action needs.
  4. RemarkCommand#execute() checks the index against the displayed list and that the note number exists. It asks the current Remark for the updated notes (withNoteAdded(), withNoteReplaced() or withNoteRemoved()), checks the total length, and creates the changed person with Person#withRemark().
  5. RemarkCommand replaces the person with Model#setPersonKeepingDisplayed() instead of Model#setPerson(). find /remark searches notes, so a changed note can stop the person from matching the current search. This method keeps the person in the displayed list anyway, so the search results, the indices on screen and the sort order stay the same until the next list, find or filter. EditCommand does the same.

Error handling: remark INDEX without a note is an error rather than a way to clear the notes, so notes are never lost because of a missing argument. A missing or invalid index or note number causes a ParseException. An index outside the displayed list, a note number the person does not have, or notes that would be too long cause a CommandException. In each case the person is unchanged.

Design considerations

Aspect: how a note is entered

  • Alternative 1 (current choice): Everything after the index is the note, with keywords only straight after the index.
    • Pros: Fast to type, and a note can contain / without being split.
    • Cons: A note cannot start with /edit, /delete or /clear as its own word.
  • Alternative 2: A prefix such as /note NOTE, parsed by ArgumentTokenizer like other commands.
    • Pros: Consistent with add and edit.
    • Cons: Longer to type, and a note containing a prefix such as /tag would be split or rejected.

Aspect: how notes are stored

  • Alternative 1 (current choice): A list of separate notes.
    • Pros: Each note can be edited or deleted by its number, without retyping the others.
    • Cons: Needs a note number for /edit and /delete.
  • Alternative 2: One block of free text that remark replaces.
    • Pros: Simpler model.
    • Cons: Changing one detail means retyping the whole remark.

Aspect: how the four formats are implemented

  • Alternative 1 (current choice): one RemarkCommand class with an Action enum, created through the factory methods add(), edit(), delete() and clear(). execute() switches on the action once to compute the notes, and getSuccessMessage() switches again for the message.
    • Pros: The shared steps (finding the person, the length check, saving) are written once, and all four formats stay in one place that matches the single remark command word.
    • Cons: Two switches on the same action, and noteIndex and note are null for actions that do not use them.
  • Alternative 2: one command class per format, e.g. AddRemarkCommand and DeleteRemarkCommand.
    • Pros: Each class holds only the fields it needs, with no switches.
    • Cons: Four classes repeat the shared steps, or need a common superclass for them.

Find command

The find command searches names using find INPUT, or one selected field using find /CRITERION INPUT. The command word and criterion are case-insensitive. Supported criteria are /name, /patientNo, /familyNo, /address, /pEmail, /fEmail, /email (either email) and /tag. It changes the displayed contacts and returns the match count without modifying stored contacts.

Parsing and phrase matching

FindCommandParser#parse() trims surrounding whitespace and collapses repeated whitespace within the input. Plain input creates a NameContainsKeywordsPredicate; criterion input creates a PersonContainsKeywordsPredicate. In both cases, the normalized input is passed as one search phrase, not as separate alternative keywords. Text matching uses case-insensitive substrings.

  • find D Est searches for the continuous phrase D Est. It matches D Est and Dr D Est Tan, but not D Tan, Est Lee or D Middle Est.
  • find alex david does not return Alex Yeoh and David Li separately; the name must contain alex david together in that order.
  • Single substrings still work: find dy matches Brandy. /name uses the same phrase semantics.
  • Phone searches require one sequence of at least two digits and match consecutive digits: 87 matches 900087000, but not 89700000. Spaces within a phone number are rejected.

PersonContainsKeywordsPredicate#test() selects the requested field before matching. Missing optional emails or tags do not match. Leading and trailing whitespace never creates an additional search term.

Search scope and execution

Search scope is determined by the active or archive list selected by the user, not by which contacts happen to be visible. The model retains this scope separately from the search predicate and sort comparator.

  • In the active scope, find searches all active contacts, replacing any previous search or filter criteria.
  • After list archive, find searches archived contacts only. Repeated searches, filters, sorting and zero-match results retain the archive scope and cannot expose active contacts.
  • list restores the active scope; list archive restores the archive scope. A search does not accumulate the previous search terms, and it preserves the current sort order.

Filter command

The filter command narrows the displayed list to contacts matching all of the given criteria: /name, /tag and /address. Within one criterion, matching any one of the values is enough, and a contact must satisfy every criterion that was given. Matching ignores case. A filter applies to the list currently shown, so it keeps the active or archived scope, and it does not modify the stored contacts.

The sequence diagram below shows a successful filter /tag HIGH command. It focuses on parsing and execution; helper calls and UI updates are omitted for clarity.

  1. LogicManager#execute() passes the input to AddressBookParser#parseCommand(), which recognises filter and creates a FilterCommandParser. It then calls parse(" /tag HIGH").
  2. FilterCommandParser#parse() first replaces every run of whitespace (spaces, tabs and newlines) with a single space, so a prefix is recognised after any whitespace and not only after a literal space. It then uses ArgumentTokenizer with the /name, /tag and /address prefixes. Name values are split on whitespace into keywords, while each /tag and /address value is kept whole, so repeating those prefixes supplies several alternatives. It creates a PersonMatchesFilterPredicate from the three lists, and a FilterCommand that holds this predicate.
  3. PersonMatchesFilterPredicate#test() treats an empty list as "criterion not applied". Within a criterion, matching any one value is enough (OR); a person must satisfy every criterion that was given (AND). Name, tag and address matching ignore case, and address matching also collapses each run of whitespace into a single space in both the stored address and the phrase.
  4. FilterCommand#execute() calls Model#filterPersonsInCurrentList(predicate). This combines the predicate with the scope of the list currently shown (active contacts after list, archived contacts after list archive), so the filtered list only contains persons in that scope who match the criteria. The scope is kept even when nothing matches, and find switches back to active contacts.
  5. The command calls Model#getFilteredPersonList() to count the persons now shown, and returns a CommandResult with the "N person(s) listed!" message.
  6. LogicManager checks FilterCommand#modifiesData(), which returns false, and skips saving.

Error handling: FilterCommandParser#parse() throws a ParseException with the command usage if there is text before the first prefix, if no criterion is given, if any prefix has an empty value, if any other token starts with / but is not one of the three prefixes (for example /patientNo), or if any /tag value is not one of HIGH, MEDIUM or LOW (case-insensitive). If /name is given more than once, ArgumentMultimap#verifyNoDuplicatePrefixesFor throws a ParseException that lists the repeated prefix. A filter with no matches succeeds, displays an empty list, and reports 0 person(s) listed!. Use list to display all active contacts again.

Sort command

The sort command changes the order in which contacts are displayed. It supports four criteria: sort priority [asc|desc], sort name [asc|desc], sort checkup [asc|desc] and sort recent.

Design. ModelManager keeps a SortedList that wraps the FilteredList, and Model#getFilteredPersonList() returns the sorted list. This means:

  • A sort is applied on top of the current filter, so filter and sort combine in either order.
  • The stored contact order is never changed. recent depends on this: the address book keeps contacts in the order they were added, so recent is the reverse of that order and needs no timestamp.
  • Commands that take an INDEX (delete, edit, view) read the displayed list, so the index shown on screen always refers to the contact that is acted on.
  • list calls Model#resetSortedPersonList(), which restores the order contacts were added.
  • Changing a contact does not move it in a sorted list. Otherwise edit 1 /name Zed under sort name would move contact 1 to the end, and the next remark 1 would change someone else. When a contact is first replaced after a sort, ModelManager records the position of every displayed contact and switches the SortedList to a comparator that orders by those positions; the replacing contact takes the position of the one it replaces. The next sort, list, find or filter drops the positions and applies the chosen sort order again.

PersonComparators provides the orderings:

  • byName(ascending) compares names ignoring case and compares each run of digits by its numeric value, so Ethan2 comes before Ethan10. It is also the tie-breaker of byPriority.
  • byCheckup(ascending) orders by checkup appointment date and time, earliest first when ascending. Contacts without a checkup appointment are always last in both directions, and ties are ordered by name. CheckupAppointment implements Comparable for this.
  • byPriority(mostUrgentFirst) orders HIGH, MEDIUM, LOW (or the reverse). Contacts without a priority tag are always last in both directions, and ties are ordered by name. In the user-facing command, desc means most urgent first, so SortCommand passes !ascending as mostUrgentFirst.

The other criteria follow the same flow, and sort recent calls Model#sortPersonsByMostRecent() instead of Model#updateSortedPersonList(comparator).

How the sort command works:

  1. AddressBookParser recognises sort and creates a SortCommandParser.
  2. SortCommandParser#parse() lowercases and splits the arguments. It throws a ParseException if there is no criterion, the criterion or direction is unknown, recent is given a direction, or there are extra arguments. Priority defaults to descending; name and checkup default to ascending. It creates a SortCommand.
  3. SortCommand#execute() calls Model#updateSortedPersonList(comparator) (or Model#sortPersonsByMostRecent() for recent) and returns a CommandResult describing the order.
  4. SortCommand#modifiesData() returns false, so LogicManager does not save. The UI observes the sorted list and reorders the contact cards.

Design considerations

Aspect: How sorting is applied

  • Alternative 1 (current choice): Wrap the filtered list in a SortedList and change only its comparator.
    • Pros: The stored order and the saved data never change, and sorting combines with find and filter in either order.
    • Cons: Indices refer to the displayed order, so every command that takes an INDEX must read the displayed list (they do).
  • Alternative 2: Reorder the contacts in the address book itself.
    • Pros: No second list to maintain.
    • Cons: Sorting would change and save the stored data, list could not restore the order contacts were added, and recent would need a timestamp.

Aspect: How recent is determined

  • Alternative 1 (current choice): Reverse the order in which contacts are stored, since new contacts are appended.
    • Pros: No new field in the model or the saved file.
    • Cons: Relies on the stored order never being changed, which is why sorting must not reorder the address book.
  • Alternative 2: Store a creation timestamp for each contact.
    • Pros: Does not depend on the stored order.
    • Cons: Needs a new field, and the saved file format and existing data files must be updated.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow. The clear command only changes the displayed list, so it does not create a new address book state.

  6. CareBook displays a confirmation.

    Use case ends.

Extensions

  • 3a. The command is missing required arguments or contains an invalid index format.

    • 3a1. CareBook shows an invalid-format error with the correct usage and leaves the contact unchanged.

      Use case resumes at step 3.

  • 4a. The index is outside the displayed list, including when the list is empty.

    • 4a1. CareBook shows an invalid-index error and leaves the contacts unchanged.

      Use case resumes at step 2.

  • 4b. The selected contact is archived and the user requests to schedule or replace an appointment.

    • 4b1. CareBook shows Appointments cannot be made with archived contacts. Unarchive the contact to do so. This error takes priority over an invalid date or time once the contact index is valid.

      Use case resumes at step 3.

  • 4c. The date/time is impossible, has the wrong format or is earlier than the current local date and time.

    • 4c1. CareBook shows the date/time validation error and preserves the existing appointment and mark.

      Use case resumes at step 3.

  • 4d. Another active contact has the requested date and time but a different family HP.

    • 4d1. CareBook shows A contact with this booking date and time already exists. Only contacts with the same family HP can be booked at the same time. Hidden active contacts are checked; archived contacts do not block the slot. No contact is changed.

      Use case resumes at step 3.

  • 4e. The user requests deletion, but the contact has no appointment.

    • 4e1. CareBook shows This contact has no checkup appointment to delete. and leaves the contact unchanged.

      Use case resumes at step 3.

  • 5a. The user assigns the same appointment again.

    • 5a1. CareBook preserves the existing checkup mark. Assigning a different appointment clears the mark.

      Use case resumes at step 6.

  • 5b. The user deletes the appointment.

    • 5b1. CareBook removes the appointment row and its [ ] or [X] indicator entirely from the contact card. The other contact details are preserved.

      Use case resumes at step 6.

  1. User requests to filter contacts by one or more criteria (name, tag, address)

  2. CareBook validates the command

  3. CareBook shows the contacts in the current list (active or archived) that match all of the criteria

Use case: Sort contacts

MSS:

  1. User requests to sort the displayed contacts by a criterion (priority, name or recent) and an optional direction

  2. CareBook validates the command

  3. CareBook reorders the displayed contacts and shows a message describing the new order

    • 2a1. CareBook shows an invalid command format error with the correct usage. The order does not change.

  • 3a. User wants to see the contacts in the order they were added again.

    • 3a1. User requests to list persons. CareBook clears the sort and shows all active contacts in the order they were added.

      Use case ends.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed
  2. Should be able to finish a command within 1 second for a contact book holding up to 1000 persons
  3. Invalid commands should show a clear error message and usage example
  4. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  5. If saving fails, the user should be told what went wrong and CareBook should keep running
  6. Should be able to handle empty or malformed commands without crashing
  7. Should run without a remote server
  8. Should be usable at all screen resolutions and scales

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Recovery: Patient is deemed to have reached their normal level of physical and physiological function
  • Relevant contacts: A patient's emergency contact, or other family contacts
  • Active contact: A contact that is not archived. list shows the active contacts
  • Archived contact: A contact moved out of the active list with archive, kept with all its details and shown by list archive
  • Displayed list: The contacts currently shown, after any list, find, filter or sort. Indices refer to this list
  • Index: The number shown next to a contact in the displayed list, starting from 1
  • Care note (note): One numbered piece of free text about a contact, such as an allergy, added with remark. A contact's notes together are its remark
  • Note number: The number shown before a note on the contact's card, used by remark INDEX /edit and /delete
  • Priority tag: A contact's priority, HIGH, MEDIUM or LOW
  • Data file: data/contacts.json, where CareBook saves the contacts automatically

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Download the JAR file and copy it into an empty folder.

    2. Open a terminal in that folder and run java -jar carebook.jar.
      Expected: The GUI opens with an empty contact list. The window size may not be optimal.

  2. Saving window preferences

    1. Resize the window to an optimal size. Move the window to a different location. Close the window.

    2. Relaunch the app with java -jar carebook.jar.
      Expected: The most recent window size and location are retained.

Viewing, clearing and exiting

  1. Start with two active contacts visible. Enter view 2.
    Expected: The second displayed contact is highlighted and its full details appear above the list; both contact cards remain visible.
  2. Enter view 3, then View 1.
    Expected: The first command reports that 3 is outside the displayed range of 1 to 2; the second is an unknown command. Neither changes the selected contact.
  3. Enter clear, then view 1.
    Expected: The list, highlight and details panel are hidden, but the contacts are not deleted. view 1 reports that no contacts are currently displayed.
  4. Enter list, then view 1 again.
    Expected: Both contacts return and the first contact can be selected. list does not reselect the previously selected contact by itself.
  5. Enter clear 1, then Clear.
    Expected: The first command reports the clear usage; the second is an unknown command. The displayed contacts stay unchanged.
  6. Enter exit 1, then Exit.
    Expected: The first reports that exit takes no arguments; the second is an unknown command. The application stays open. Enter lowercase exit to close it, then relaunch CareBook and enter list. The same two contacts are still saved.

Adding a person

  1. Adding contacts with similar details

    1. Prerequisites: Use a test address book with no contact named Kim Lee and no patient phone numbers 91001001 or 91001002.

    2. Test case: ADD /name Kim Lee /patientNo 91001001 /familyNo 92002001 /address 1 Test Street
      Expected: A contact named Kim Lee is added. Command capitalization and repeated name spaces are accepted.

    3. Test case: add /name Kim Lee /patientNo 91001002 /familyNo 92002001 /address 2 Test Street
      Expected: A second contact is added despite sharing a name and family phone number. Both patient emails are absent.

    4. Test case: Add another contact with patient phone 91001001, or reuse a non-empty patient email already in the test address book.
      Expected: No contact is added. Duplicate detection includes hidden and archived contacts.

    5. Test case: add /name Kim Lee /patientNo 91001003 /familyNo 92002001 /address 1TESTstreet
      Expected: No contact is added. The same-address warning asks for a name differentiator.

    6. Test case: Repeat the previous command with /name Kim Lee 2.
      Expected: The contact is added because the name now distinguishes it.

  2. Rejecting invalid prefixes and literal slashes

    1. Test case: add /name Test Patient /patientNo 91001004 /familyNo 92002001 /address 4 St /phone 123
      Expected: Invalid command format. /phone 123 is not saved into the address.

    2. Other incorrect address arguments to try: /addressExtra 4 St and /address 4/5 Main St.
      Expected: No contact is added; the usage explains that / is reserved for valid prefixes.

Finding contacts

  1. Phrase matching and whitespace

    1. Prerequisites: Active contacts named D Est, Dr D Est Tan, D Tan, Est Lee, D Middle Est, Alex Yeoh, David Li and Brandy.

    2. Test case: find D Est
      Expected: D Est and Dr D Est Tan match. D Tan, Est Lee and D Middle Est do not match. find /name D Est and mixed-case FiNd /NAME d est give the same results.

    3. Test case: find alex david
      Expected: Neither Alex Yeoh nor David Li matches separately. A name containing Alex David would match.

    4. Test case: find dy
      Expected: Brandy matches the contiguous substring. Surrounding spaces do not affect the search.

    5. Test cases: find, find Alice /address A and find /name Alice /address A.
      Expected: The same invalid-format response with usage and supported criteria; the current display is unchanged.

  2. Retaining archive scope

    1. Prerequisites: At least one active and one archived contact with Kim in their names.

    2. Test case: Run list archive, then find Kim.
      Expected: Only archived matches appear.

    3. Test case: Run find NobodyMatchesThis, then sort name, then find Kim.
      Expected: The first search shows zero matches; the final search still returns only archived matches.

    4. Test case: Run filter /name Kim, then find Kim, then list, then find Kim.
      Expected: The search after the filter stays within archived contacts. After list, only active matches appear.
